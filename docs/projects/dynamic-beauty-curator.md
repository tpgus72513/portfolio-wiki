# 다이내믹 뷰티 큐레이터

> 사람마다 다른 피부 정보와 매일 달라지는 환경 조건을 하나의 추천 흐름으로 연결하고, 외부 데이터가 불안정해도 시연 가능한 MVP를 설계했습니다.

## 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 형태 | 팀 프로젝트 내 애플리케이션 구현 담당 |
| 기간 | 2026.05.13 ~ 2026.05.29 |
| 역할 | 기획, 웹 UI, 백엔드 API 구현 |
| 협업 | 피부 분석 모델은 팀원이 담당하고, 서비스 연결을 함께 진행 |
| 주요 기술 | Python, FastAPI, JSON 기반 매칭 룰북, 외부 환경 API, fallback 데이터 |

## 요약

- **문제:** 피부 타입이 같더라도 미세먼지, 자외선, 수질처럼 현재 환경이 달라지는데 기존 추천은 정적인 사용자 정보에 머무르는 경우가 많습니다.
- **접근:** 위치와 피부 타입을 입력받아 환경 등급을 조회하고, 조건에 맞는 추천 룰을 JSON으로 반환하는 API를 설계했습니다.
- **결과:** 추천 요청·응답과 fallback 경로를 구현하고 웹 UI에서 핵심 사용자 흐름을 확인했습니다.
- **핵심 배움:** 모델을 만드는 일과 실제 서비스에 연결하는 일은 서로 다른 문제이며, 통합 인터페이스를 초기에 합의해야 합니다.

## 배경과 목적

건성, 지성, 복합성처럼 개인마다 기본 피부 상태가 다르고, 같은 사람도 위치와 시점에 따라 미세먼지나 자외선에 다르게 노출됩니다. 그럼에도 하나의 고정된 제품이나 루틴을 계속 사용하는 문제에서 출발했습니다.

프로젝트의 핵심 가설은 **정적인 피부 정보와 동적인 환경 정보를 함께 보면 그날 필요한 관리 방법을 더 구체적으로 제안할 수 있다**는 것이었습니다. 분석 결과를 발표 자료에만 남기지 않고, 사용자가 직접 입력하고 결과를 확인할 수 있는 웹 기반 MVP로 구현하는 것을 목표로 했습니다.

## 내가 맡은 역할과 기여

### 1. 기획과 사용자 흐름

- 사용자 위치와 피부 타입을 입력으로 받고 추천 루틴을 결과로 보여주는 핵심 흐름을 정했습니다.
- 모바일 앱을 최종 형태로 가정하고 웹에서도 촬영과 추천 과정을 확인할 수 있도록 화면을 구성했습니다.
- 짧은 프로젝트 기간 안에 추천 흐름을 우선 검증하고, 부가 인터랙션과 완전한 모델 통합은 후속 범위로 구분했습니다.

### 2. 백엔드 추천 API

- FastAPI로 헬스 체크와 `POST /recommend` 엔드포인트를 구성했습니다.
- 위치, 피부 타입, 미세먼지 등급, 자외선 등급을 추천 룰과 연결했습니다.
- 일치하는 조건이 없을 때 기본 루틴을 반환하도록 해 빈 결과를 방지했습니다.
- 환경 API 호출이 실패하면 미리 준비한 지역별 시드 데이터로 전환하고, 응답에 `is_fallback`을 포함해 실제 데이터와 대체 데이터를 구분했습니다.

### 3. 웹 UI와 통합 시도

- 사용자가 카메라 촬영 흐름과 추천 화면을 직접 경험할 수 있는 웹 UI를 구현했습니다.
- 팀원이 만든 피부 분석 모델을 서비스에 연결하는 작업을 진행했습니다.
- 프론트엔드와 백엔드를 분리해 추천 결과를 화면에 전달하는 구조를 구성했습니다.

## 핵심 설계 결정

### 매칭 룰북을 서비스 경계로 사용

분석 결과를 바로 화면 코드에 넣지 않고, 피부 타입과 환경 등급을 키로 사용하는 JSON 룰북으로 분리했습니다. 백엔드는 룰북을 읽어 추천 카테고리, 성분, 피해야 할 성분을 반환합니다.

이 구조는 데이터 분석 결과가 바뀌어도 API와 화면 전체를 다시 작성하지 않고 룰북을 교체할 수 있다는 장점이 있습니다.

### 외부 API 실패를 정상 흐름으로 처리

발표 환경에서는 API 키, 네트워크, 응답 형식 때문에 시연이 중단될 수 있습니다. 예외가 발생하면 서버를 종료하는 대신 fallback 데이터로 같은 추천 흐름을 유지했습니다.

단, fallback 사용 여부를 숨기지 않고 응답에 표시했습니다. 시연 안정성과 데이터 투명성을 함께 지키기 위한 선택이었습니다.

## 가장 어려웠던 점: 피부 분석 모델 통합

팀원이 별도로 만든 피부 분석 모델을 웹의 카메라 입력부터 추천 API까지 하나의 흐름으로 연결하는 일이 가장 어려웠습니다. 모델이 존재하는 것과 사용자가 촬영한 이미지가 서비스 안에서 분석 결과로 돌아오는 것은 별개의 통합 작업이었습니다.

프로젝트 기간 안에는 촬영 UI와 추천 엔진의 핵심 흐름을 우선 완성했고, 카메라로 직접 촬영하며 화면 동작을 확인했습니다. 다만 촬영 결과를 피부 분석 모델에 전달하고 자동으로 피부 상태를 반환받는 연결은 완료하지 못했습니다. 이 범위를 발표에서 완성된 기능처럼 설명하지 않고 다음 마일스톤으로 명확히 남겼습니다.

## 결과 및 검증

- 서버 헬스 체크와 추천 엔드포인트의 요청·응답 구조를 확인했습니다.
- 피부 타입과 환경 등급에 맞는 룰이 있으면 해당 루틴을, 없으면 기본 루틴을 반환하는 흐름을 점검했습니다.
- 외부 API 실패 시 시드 데이터로 전환되고 `is_fallback: true`가 반환되는 경로를 확인했습니다.
- 웹에서 카메라 촬영 화면과 추천 결과 흐름을 직접 실행해보며 사용자 관점으로 점검했습니다.

## 한계와 다음 단계

- 카메라 기반 피부 분석 모델은 학습 결과와 UI가 있었지만 서비스 내부 연결은 완료하지 못했습니다.
- 자외선 API 응답 파싱은 코드에 골격만 남았고, 수질은 실시간 API가 아니라 정적·시드 데이터를 사용했습니다.
- 리뷰 수집 코드의 제품 URL과 CSS selector 일부는 실제 운영값이 아닌 예시였습니다.
- 추천 룰의 조합이 제한적이어서 일치하지 않는 요청은 기본 루틴으로 처리했습니다.
- 의료적 판단이나 치료 추천이 아니라 서비스 가설을 확인하기 위한 비상업적 MVP입니다.

다음 버전에서는 먼저 모델의 입력·출력 계약과 배포 방식을 고정하고, 테스트 이미지 세트로 `촬영 → 분석 → 추천` 전체 흐름을 자동 검증하겠습니다. 이후 외부 환경 API별 성공·실패를 독립적으로 처리해 하나의 API 장애가 전체 데이터를 fallback으로 바꾸지 않도록 개선하고 싶습니다.

## 이 프로젝트로 보여준 역량

- 분석 아이디어를 사용자가 실행할 수 있는 웹·API 흐름으로 구체화한 경험
- 팀원이 만든 모델과 애플리케이션 사이의 통합 문제를 발견하고 범위를 조정한 판단
- 외부 API 장애를 고려한 fallback 설계
- 구현한 기능과 미완료 기능을 구분해 설명하는 기술 커뮤니케이션
