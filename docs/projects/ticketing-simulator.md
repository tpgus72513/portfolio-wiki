# 올클(AllCle) — 야구 티켓팅 연습 시뮬레이터

> 구현 난도가 높은 실시간 경쟁은 MVP 범위에서 제외하고, 티켓팅의 핵심 단계와 긴장감을 반복해서 연습할 수 있는 1인 시뮬레이션의 백엔드 흐름을 구현했습니다.

## 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 형태 | 팀 프로젝트 |
| 역할 | 팀장, 기획, 백엔드 개발 |
| 대상 | 수강신청·야구 티켓팅처럼 짧은 시간 안에 판단하고 입력해야 하는 상황을 연습하려는 사용자 |
| 주요 기술 | Node.js, Express, TypeScript, Supabase(PostgreSQL), JWT, zod |
| 구현 범위 | 익명 인증, 경기 선택, CAPTCHA, 좌석 선택, 결제 시뮬레이션, 점수 산출 |

## 요약

- **문제:** 실제 티켓팅은 기회가 적고 실패 비용이 커서 반복 연습하기 어렵습니다.
- **접근:** 티켓팅 과정을 짧은 상태 머신으로 모델링하고, 실제 결제와 공유 좌석 없이도 긴장감을 재현했습니다.
- **결과:** 백엔드 핵심 흐름을 5개 스프린트로 구현하고, CAPTCHA부터 점수 산출까지 대표 시나리오를 단계별로 검증했습니다.
- **핵심 배움:** 기능을 많이 넣는 것보다 MVP에서 검증할 경험을 먼저 정하고, 구현하지 않은 범위를 명확하게 설명하는 것이 중요했습니다.

## 배경과 목적

수강신청이나 인기 경기 티켓팅은 짧은 시간 안에 대기, 문자 입력, 좌석 판단, 결제 입력을 연속으로 처리해야 합니다. 하지만 실제 상황에서만 연습할 수 있고, 한 번의 실수가 곧 실패로 이어집니다.

올클은 이 과정을 웹에서 반복할 수 있도록 만든 연습용 시뮬레이터입니다. 실제 예매 시스템을 복제하기보다 사용자가 연습해야 할 흐름인 `시작 → CAPTCHA → 좌석 선택 → 결제 → 결과`에 집중했습니다.

## 내가 맡은 역할과 기여

### 1. 팀장 및 기획

- 티켓팅 경험을 대기열, CAPTCHA, 좌석 선택, 결제, 결과 단계로 분해했습니다.
- 난이도, 매진 확률, 입력 시간, 실수 횟수를 점수에 반영하는 기준을 정리했습니다.
- 초기 API 명세와 실제 구현의 차이를 추적하고, 프론트엔드 팀원이 사용할 실제 API 레퍼런스와 인수인계 문서를 작성했습니다.

### 2. 백엔드 개발

- 시뮬레이션 한 판을 상태 머신으로 모델링하고 각 단계의 완료 시각을 데이터베이스에 기록했습니다.
- 익명 사용자에게 JWT를 발급하고, 한 사용자가 동시에 하나의 진행 중 시뮬레이션만 갖도록 제약을 설계했습니다.
- CAPTCHA 발급·검증, 좌석 매진 판정, 결제 단계, 점수 산출 로직을 스프린트 단위로 구현했습니다.
- 클라이언트 시간이 아닌 서버의 timestamp 차이로 단계별 소요 시간을 계산했습니다.

## 핵심 설계 결정

### 상태 머신으로 진행 순서 보장

각 요청을 독립적인 API로만 처리하면 CAPTCHA를 통과하지 않고 좌석을 선택하거나, 좌석 없이 결제를 완료하는 잘못된 흐름이 생길 수 있습니다. 이를 막기 위해 시뮬레이션 상태와 단계별 timestamp를 기준으로 다음 행동의 허용 여부를 검사했습니다.

### 공유 좌석 대신 결정론적 매진 시뮬레이션

실제 다중 사용자 티켓팅은 공유 좌석, 좌석 잠금, 동시성 제어가 필요합니다. 프로젝트 기간과 팀의 경험을 고려하면 이 범위까지 안정적으로 완성하기 어려웠습니다.

대신 시뮬레이션별 seed와 좌석 구역의 인기도, 난이도를 조합해 매진 여부를 항상 같은 결과로 계산했습니다. 서버에 모든 좌석 상태를 저장하지 않아도 한 판 안에서는 결과가 일관되며, 사용자는 인기 좌석이 빠르게 사라지는 경험을 할 수 있습니다.

이 선택으로 **실시간 경쟁 자체**보다 **빠른 판단을 연습하는 경험**을 먼저 검증했습니다.

## 문제 해결 경험

### 좌석이 전부 매진되는 버그

초기에 좌석 인기도를 `0~1` 범위의 값으로 가정했지만 실제 데이터는 `1~5` 정수였습니다. 이 값을 그대로 매진 확률 계산에 넣어 임계값이 지나치게 커졌고, 거의 모든 좌석이 매진되는 문제가 발생했습니다.

데이터 스키마와 계산식을 다시 대조한 뒤 인기도를 `popularity / 5`로 정규화했습니다. 이 경험을 통해 계산 로직만 확인해서는 부족하며, 입력 데이터의 단위와 범위를 계약처럼 관리해야 한다는 점을 배웠습니다.

### 명세와 실제 구현의 차이

개발 중 인증 방식, ID 타입, API 경로가 초기 명세와 달라졌습니다. 변경 내용을 구두로만 공유하면 프론트엔드 통합에서 같은 오류가 반복될 수 있어, 실제 코드 기준 API 레퍼런스와 명세 대비 변경표를 별도로 작성했습니다.

## 결과 및 검증

- CAPTCHA 발급·통과, 가용 좌석 선택, 결제 시작, 완료와 점수 저장까지 전체 흐름을 HTTP 요청으로 단계별 실행했습니다.
- 대표 검증 사례에서 산출된 점수 `15,275`가 세부 점수 `9,547 × 난이도 배수 1.6`의 반올림 결과와 일치하는지 손으로 다시 계산했습니다.
- 통합된 웹 화면을 팀원이 직접 실행하며 티켓팅 흐름을 확인했습니다.

## 한계와 다음 단계

- 대기열은 프론트엔드 mock으로 표현했으며 WebSocket·Redis 기반 실시간 큐는 구현하지 않았습니다.
- 여러 사용자가 같은 좌석을 두고 경쟁하는 공유 좌석 풀과 좌석 잠금은 포함하지 않았습니다.
- 실제 결제 모듈을 연결하지 않았고, 결제 화면 체류 시간만 시뮬레이션에 사용했습니다.
- 프론트엔드와 백엔드의 전체 API 통합, 자동화 테스트, 결과 카드 이미지 생성은 후속 작업으로 남았습니다.

다음 버전에서는 Redis 기반 대기열과 좌석 hold 만료 정책을 먼저 설계한 뒤, 두 브라우저가 같은 좌석을 선택하는 동시성 시나리오를 자동화 테스트로 검증하고 싶습니다.

## 이 프로젝트로 보여준 역량

- 요구사항을 상태 머신과 API 계약으로 변환하는 능력
- 데이터 범위 오류를 원인까지 추적하고 계산식을 수정한 경험
- 구현 난도와 일정에 맞춰 기능 범위를 줄이고 그 근거를 설명하는 판단
- 프론트엔드 협업을 위한 API 문서와 인수인계 자료 작성
