# 세종페이(PAYUS) — 캠퍼스 전용 QR 간편결제 플랫폼

> 학생과 지역 가맹점을 연결하는 QR 간편결제 MVP에서 프론트엔드를 담당했습니다. 화면 구현뿐 아니라 QR 결제 흐름 연결, 디자인 시스템 구성, 팀 저장소에서 삭제된 앱 소스 복구와 병합까지 수행했습니다.

## 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 형태 | 4인 팀 프로젝트, 고려대학교 세종캠퍼스 KUS R&SD 2026 |
| 역할 | 프론트엔드 개발 |
| 대상 | 캠퍼스 주변 상권을 이용하는 학생과 지역 가맹점 |
| 주요 기술 | React 18, Vite 5, React Router, TanStack Query, Axios, MSW, Tailwind CSS, html5-qrcode |
| 구현 범위 | 학생·가맹점 화면, 공통 컴포넌트와 디자인 토큰, API 서비스 계층, QR 스캔·결제 화면 연결 |

## 요약

- **문제:** 학생과 캠퍼스 주변 가맹점을 연결하면서 결제, 혜택, 매장 탐색을 하나의 경험으로 제공할 수단이 필요했습니다.
- **접근:** 학생·가맹점 사용 흐름을 화면 단위로 나누고, 공통 컴포넌트와 API 서비스 계층을 구성해 QR 결제 전후의 경험을 연결했습니다.
- **결과:** 프론트엔드 앱의 주요 화면 구조와 디자인 시스템을 구성하고 QR 스캐너를 결제 흐름에 연결했습니다. 개발 중 삭제된 앱 소스 46개도 Git 이력에서 복구해 다시 빌드 가능한 상태로 만들었습니다.
- **핵심 배움:** 팀 프로젝트에서는 화면 구현만큼 API 계약, 브랜치 병합, 복구 가능한 커밋과 검증 기록이 중요하다는 점을 배웠습니다.

## 배경과 목적

세종페이는 학생이 학번 인증 후 지갑을 충전하고, 캠퍼스 주변 가맹점에서 QR로 결제하며 캐시백·스탬프·쿠폰 혜택을 받는 과정을 검증한 학술 목적의 MVP입니다.

프론트엔드에서는 학생과 가맹점주가 서로 다른 기능을 사용하므로 역할별 정보 구조가 필요했습니다. 학생에게는 매장 탐색, 충전, QR 스캔, 결제 확인, 영수증과 혜택 내역이 중요했고, 가맹점주에게는 QR 관리, 매출·정산 확인, 쿠폰 관리가 필요했습니다.

## 내가 맡은 역할과 기여

### 1. 학생·가맹점 화면 구조 구현

- 로그인·회원가입과 보호된 경로를 구성하고 인증 상태를 `AuthContext`에서 관리했습니다.
- 학생용 홈, 지도, 매장 상세, 충전, 쿠폰, QR 스캔, 결제 확인·완료, 영수증, 거래 내역과 알림 화면을 구성했습니다.
- 가맹점용 홈, QR 관리, 매출, 정산, 쿠폰과 설정 화면을 역할별 흐름에 맞춰 분리했습니다.
- 공통 레이아웃과 버튼, 입력창, 카드, 모달, 빈 상태 컴포넌트를 재사용할 수 있게 정리했습니다.

### 2. 디자인 시스템과 개발 기반 구성

- Tailwind CSS 설정, 디자인 토큰과 Pretendard 글꼴을 실제 앱에 연결했습니다.
- 색상·간격·컴포넌트 상태를 공통 규칙으로 관리해 여러 화면의 표현을 맞췄습니다.
- Vite 개발 서버와 `/api` 프록시, 공통 Axios 인스턴스를 사용해 화면 코드가 서버 주소와 인증 처리를 반복하지 않게 했습니다.

### 3. 백엔드와 독립적으로 개발할 수 있는 구조

- MSW와 가맹점 목 데이터를 추가해 백엔드가 준비되지 않은 상황에서도 지도와 매장 흐름을 확인할 수 있게 했습니다.
- 사용자, 거래, 스탬프, 알림, 가맹점, 쿠폰별 API 호출을 서비스 파일로 분리했습니다.
- QR 스캐너 결과를 결제 확인 화면으로 전달하고, 결제 전후 화면이 이어지도록 라우팅과 데이터 흐름을 연결했습니다.

## 핵심 설계 결정

### 역할별 화면과 공통 컴포넌트 분리

학생과 가맹점주는 필요한 정보와 행동이 다르지만 버튼, 카드, 모달과 페이지 레이아웃은 공유할 수 있습니다. 화면은 역할별 디렉터리로 분리하고 표현 요소는 공통 컴포넌트로 모아, 기능의 경계와 디자인 일관성을 함께 유지했습니다.

### API 서비스 계층과 MSW 사용

페이지에서 직접 HTTP 요청을 작성하면 인증 처리와 오류 형식이 화면마다 달라질 수 있습니다. 공통 Axios 인스턴스와 도메인별 서비스 파일을 두고, 개발 중에는 MSW가 같은 호출 구조로 응답하도록 했습니다.

이 구조 덕분에 화면은 백엔드의 준비 여부와 관계없이 개발할 수 있었고, 실제 API를 연결할 때도 페이지 전체를 다시 작성하지 않고 서비스 계층을 중심으로 조정할 수 있었습니다.

## 문제 해결 경험

### 삭제된 프론트엔드 앱 소스 46개 복구

프론트엔드 작업물을 업데이트하는 과정에서 `main.jsx`, `App.jsx`, 페이지, 서비스, 인증 컨텍스트 등 동작하던 앱 소스 46개가 한 커밋에서 삭제됐습니다. 그 결과 Vite가 `/src/main.jsx`를 찾지 못해 앱이 실행되지 않았습니다.

삭제 직전 커밋과 다른 팀원의 원격 브랜치를 비교해 원본 파일이 남아 있는 지점을 찾았습니다. 저장소 전체를 과거로 되돌리지 않고 삭제된 파일만 복구해 다른 팀원의 변경을 보존했습니다. 이후 `FE` 폴더를 `frontend`로 정리하고 `dist/`를 Git 추적 대상에서 제외했습니다.

히스토리를 다시 쓰는 `reset --hard`, rebase, force push는 사용하지 않았으며, 복구와 폴더 정리를 별도 커밋으로 나눴습니다. 마지막으로 `npm run build`를 실행해 앱이 다시 빌드되는 것을 확인했습니다.

### 복구와 디자인 통합의 범위 분리

삭제된 앱을 복구한 직후에는 기존 화면과 새 디자인 산출물이 동시에 존재해 스타일이 완전하게 일치하지 않았습니다. 이때 복구와 디자인 변경을 한 번에 처리하면 문제가 생겼을 때 원인을 구분하기 어렵다고 판단했습니다.

먼저 진입점, 라우팅, 페이지와 서비스 파일을 원래 상태로 복구해 실행 가능성을 확인했습니다. 디자인 토큰과 공통 스타일 연결은 다음 커밋으로 분리했습니다. 이 방식으로 기능 복구의 검증 기준과 시각적 개선의 검증 기준을 분리할 수 있었습니다.

## 결과 및 검증

- 프론트엔드 복구 후 `npm run build`가 통과하는 것을 확인했습니다.
- Vite 개발 서버에서 앱 진입점과 주요 라우팅이 다시 동작하는 것을 확인했습니다.
- QR 스캐너를 결제 화면에 연결하고 스캔 이후 확인 화면으로 이동하는 흐름을 점검했습니다.
- Git 이력에는 `tpgus72513` 명의의 프론트엔드 관련 커밋 12개가 남아 있습니다.

## 한계와 다음 단계

- 실제 금융 서비스를 운영한 것이 아니라 학술 프로그램에서 결제 경험을 검증한 MVP입니다.
- 프론트엔드에는 자동화 테스트 스크립트가 없어 빌드와 수동 실행을 중심으로 검증했습니다.
- JavaScript와 일부 TypeScript 디자인 산출물이 함께 있어 파일 형식과 디렉터리 구조를 더 일관되게 정리할 필요가 있습니다.
- 다음 단계에서는 QR 스캔부터 결제 완료까지의 대표 흐름을 브라우저 자동화 테스트로 만들고, 백엔드 오류·중복 요청·만료된 QR에 대한 사용자 피드백을 검증하고 싶습니다.

- 공통 컴포넌트와 디자인 토큰으로 여러 화면의 일관성을 관리한 경험

- 복구, 구조 변경, 디자인 통합을 나누어 검증 가능한 단위로 작업한 협업 방식
